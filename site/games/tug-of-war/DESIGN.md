# T1 紅藍格鬥（扣血對戰）DESIGN（回推八步驟）

> **資料夾名稱沿用 `tug-of-war`**，game id 仍是 `'tug-of-war'`（已對外流通的網址不改）。
> 2026-10-17 改版：原本的拔河在兩隊實力相當時會來回拉很久、可能下課前分不出勝負；改為「紅藍角色扣血」，血量只減不增，一定在時限內結束，與本專案的格鬥場系列一致。

日期：2026-10-17。定位：研習第二小時「遊戲化評量」模板。老師只換題庫就能使用，但仍守住三件事：**誘答對準真實誤解、錯了有診斷回饋、每個作答都留痕**。
原型：影片「學生想破關，還是想下課」的遊戲 A：把測驗包裝成紅藍對戰；扣血規則參考多項式除法格鬥場（血量 360／540／720 的人數比例精神）。範例題庫為八上「多項式除法」12 題；另附七上「比與比例式」8 題示範換題庫。

## 1. 教學目標
以範例題庫為例，學生能：
- 判斷多項式除法商式的次數（被除式次數 − 除式次數）。
- 直式時依降冪排列並在缺項補 0。
- 相減時把乘回的式子整個變號。
- 依「餘式次數小於除式次數」判斷何時停止，並知道餘式不一定是 0。
- 正確寫出「被除式＝除式×商式＋餘式」並用它反推被除式。

換題庫時，這一節由老師依新單元改寫；模板本身只提供「快速檢核＋誤解診斷」的流程。

## 2. 評量證據與記錄欄位
證據是「學生在時間壓力下，面對對準誤解的誘答，選了哪一個／輸入了什麼／排了什麼順序」。
每次作答寫一筆 `kind:'answer'` 事件，欄位在設計這一步就決定好：

| 欄位 | 意義 |
|------|------|
| `qid`、`type` | 哪一題、題型 |
| `given` | 學生實際的作答（選項純文字、輸入原文、排序以 → 連接） |
| `correct` | 是否正確 |
| `misconception` | 誤解代碼（英文 snake_case，穩定分群用） |
| `ms` | 從出題到作答的毫秒數 |
| `attempt` | 第幾次嘗試（1＝第一次；看過診斷後再試為 2 以上） |
| `team`、`damage`、`combo`、`foeHp` | 隊伍、實際造成的傷害（答錯為 0）、是否連擊加成、攻擊後對手剩餘血量 |
| `counted` | false 表示格式看不懂，不計分但留痕 |
| `weight`、`bank`、`round` | 題目權重、題庫、第幾局 |

另有 `join`、`match_start`（含開賽鎖定的 `maxHp`）、`match_end`（含最終 `hp`／`maxHp`、勝隊、結束原因 ko／time／teacher、兩隊人數與答對數）。
發展式出招另寫 `step_check`（沿用 step-board 欄位＋`damage`、`combo`、`final`）、`hint`、`problem_done`。
老師報告用「首次正確率」（只看 attempt=1）作為主要指標，因為再試一次時選項已被刪去，不能代表獨立完成。

## 3. 核心機制
- 紅藍兩隊，每人用自己的 iPad，一題接一題（每人題序打亂，出完一輪才重洗）。
- 兩隊各有一個角色（紅左、藍右）與血條。血量依**對手**人數在開賽時鎖定：1 人 100、2 人 150、3 人以上 200（對手越多、攻擊越快，血要越厚；1v2、2v3 才不會一面倒）。
- 答對：攻擊對方。傷害＝(10 + 4 ×(權重 − 1)) × 3 ÷ max(3, 我方人數)，四捨五入、至少 1（權重 1／2／3 = 10／14／18）。人數校正讓「隊伍答對率」而不是「人多」決定勝負。同一人連續答對第 3 題起 ×1.2（不疊加）。
- 勝負：一方血量 ≤ 0 立即結束、另一方勝；時間到（或老師提前結束）比剩餘血量比例，相同平手。血量只減不增，所以實力相當也一定在時限內分出結果或明確平手。
- 答錯：不攻擊、**不扣自己的血**，立刻顯示「該誘答」的診斷句，冷卻 3 秒後可「再試一次（傷害減半）」或「下一題」（跳過時顯示正確答案）。

### 兩種出招方式（同一個對戰外殼）
- **評量式（`play:'quiz'`，預設）**：答題庫題目，答對一題攻擊一次。本文件第 1～7 節以此為主。
- **發展式（`play:'steps'`，`content` = linear-equation／proportion／poly-division）**：重用 T3 解題板的 content，學生點卡片放進卡槽、一行一行建構解題過程，按「檢查這一步」成立就攻擊（每步 weight 1，整題最後一步為最後一擊 weight 2）；錯了顯示該步的誤解診斷（kind 來自 content）、冷卻 3 秒、不攻擊；該步錯過或用到第 3 層提示後再成立，傷害減半。遊戲動詞＝「建構每一步的數學關係」，第二問檢驗通過程度高於評量式。

### 兩問檢驗（誠實回答）
1. **拿掉數學，還玩得下去嗎？**（評量式）玩得下去。扣血對戰是「答對就攻擊」的外包裝，換成歷史題也能玩，這是**評量包裝型**，不是內生整合（intrinsic integration）的遊戲。依本專案規範，它**不能**當作建構概念的發展活動。
   它仍可作為形成性評量的理由：
   - 遊戲動詞雖然只是「選／填／排」，但每個誘答都對準一個已知誤解，學生選了哪個誘答就是可分析的證據（第 2 步）。
   - 答錯當下就有針對該誘答的診斷，並給「再試一次」的退路，回饋本身是學習機會，不只是扣分。
   - 隊伍競爭與人數校正提供短時間的投入動機，讓全班在 5 分鐘內產生大量作答資料，老師可立即看誤解排行決定下一步教學。
   限制：
   - 只能檢核「辨認與程序判斷」，不能證明學生能自己建構完整直式；需搭配紙筆或建構型遊戲（如多項式除法格鬥場）。
   - 選擇題有猜測成分；再試一次時選項會變少，所以報告分開呈現首次正確率。
   - 時間壓力可能放大焦慮或鼓勵猜題；冷卻 3 秒是為了降低亂猜的收益。
   - 題庫品質決定一切：誘答若不對準真實誤解，留痕就失去診斷價值。
2. **遊戲動詞＝達標證據裡的行為嗎？** 部分符合。證據行為是「在誘答中辨認正確做法／算出關鍵中介量／排出正確步驟」，與遊戲動詞一致；但教學目標中的「完整執行長除法」不在本遊戲的證據範圍內，屬層次較低的檢核。

## 4. 誤解清單（範例題庫）
| kind | 誤解 | 對應題 |
|------|------|--------|
| `quotient_degree` | 商的次數算錯（次方沒相減或相加） | 01、04、12 |
| `partial_division` | 多項式除以單項式只除了部分項 | 01、02、11 |
| `self_division_zero` | 同類項相除得 1 卻當成 0 | 01 |
| `subtraction_sign` | 相減時沒有整個變號 | 02、06、07、12 |
| `missing_zero_term` | 缺項沒補 0 | 03、06、12 |
| `degree_alignment` | 補 0 的位置或降冪排列錯 | 03 |
| `remainder_degree` | 餘式次數不小於除式就停止 | 05、06 |
| `remainder_must_zero` | 以為餘式必須為 0 | 05、11 |
| `remainder_coefficient` | 用係數大小判斷停止 | 05 |
| `remainder_divided` | 把餘式再除成分數 | 11 |
| `quotient_coefficient`、`division_sign` | 商的係數或正負號錯 | 07 |
| `identity_structure`、`identity_roles`、`remainder_as_quotient` | 「被除式＝除式×商式＋餘式」寫錯 | 09、10 |
| `expansion_error` | 乘開時合併同類項錯 | 09 |
| `procedure_order` | 「求商→乘回→相減」順序不清 | 08 |

規則：誘答文字是「帶這個誤解的學生真的會寫出的結果」，不是隨便的 ±1。一題中同一個 kind 可以有不同診斷句（例如 04 題三個誘答都是 `quotient_degree`，但分別對應「沒減」「相加」「拿除式次數」）。

## 5. 回饋與計分
- 答對：攻擊對方角色（權重 1～3 → 傷害 10／14／18，人數校正後），對方角色震動閃紅並飄出傷害數字（`prefers-reduced-motion` 時只閃框不震動）；連對 3 題起 ×1.2。
- 答錯：不攻擊、不扣自己血，但冷卻 3 秒並顯示診斷（錯誤有代價）；可再試一次但傷害減半（有退路）。
- 格式看不懂（例如輸入「三分之一」）：不計分、不冷卻，提示可接受格式，仍留痕 `format_invalid`。
- 結算畫面列出本局最常犯的 1～3 個誤解（用 kind 對應中文說明），引導學生回頭想。

## 6. 鷹架分層
- 題庫內以權重區分：1＝單一觀念辨認；2＝需算出中介量或判斷停止條件；3＝完整小題（商與餘式、缺項多的除法）。
- 輸入題提供螢幕數字鍵盤（含 −、/、.），分數、小數、帶分數、全形都接受。
- 排序題可逐一撤回或全部撤回。
- 跳過時顯示上一題正確答案。
- 單人練習模式（對電腦角色，三種難度：電腦每 8／6／4 秒打你 5／6／6 點，你的血量 100）可在課前或課後個別練習；`&play=steps` 可改用發展式出招。

## 7. 課堂運作（45 分鐘建議）
- 0–10 分：教師講解或複習（遊戲不取代教學）。
- 10–13 分：老師批量開房、投影 QR；學生加入後自動分隊。
- 13–18 分：第一局 5 分鐘（系統計時，到期自動結算；老師可提前結束）。
- 18–28 分：老師開報告頁，看誤解排行最高的 2～3 個 kind，全班討論。
- 28–33 分：「再來一局」（隊伍不變），檢查討論後是否改善。
- 33–45 分：紙筆出口題（完整直式），補足遊戲無法檢核的建構能力。
到期推進：任何一端（老師或學生）發現時間已到，都可以用 transact 把房間改成 ended，transact 保證只成功一次；學生端加 0.5～2 秒隨機延遲，避免全班同時寫入。

## 8. 資料留痕與技術
- 純 HTML＋ES modules，共用 `../../shared/backend.js`（Cloudflare 模式：Durable Objects 房間＋D1 事件；或本機模式）。
- 房間 state 只存 `{v:2, status, round, durationSec, startedAt, endsAt, endedAt, hp:{red,blue}, maxHp:{red,blue}, winner, endReason, ns, bank, play, content, players:{id:{team, correct, wrong, streak, joinedAt}}}`；30 人整場作答後約 2～3 KB，遠低於 256 KB 上限。
- 所有房間改動都經 `transact`（樂觀鎖重試），純函式寫在 `logic.js` 並有 node 測試。
- 事件透過 `logEvent` 寫入 `mg_events`，失敗會存本機自動補送。單人模式 `room` 為 null。
- 報告頁 `report.html` 依房號或全部讀取，誤解以 `misconception` 代碼分群（不用帶數字的文字），可匯出逐人、每題、誤解排行、逐筆事件四種 CSV。
- 身分只用「班級-座號」或暱稱，不收真實姓名。

## 驗收狀態
- node 測試：答案正規化、判題、隊伍平衡、血量初始化與鎖定、傷害計算（星等、人數校正、再試減半、連擊）、歸零即勝、時間到比例判勝與平手、老師結束判勝、電腦攻擊、舊 rope 資料相容、30 人打得完、到期只成功一次、出題不重複、報告彙整、兩份題庫格式；發展式：出招設定、三種 content 照正解逐步攻擊、錯步不攻擊與減半。
- 尚待：瀏覽器多分頁實測、iPad Safari 真機、整班 30 人同時作答的 Cloudflare（Durable Objects／D1）負載。
